## 3. High-leverage open issues (do these first)

### 3.1 ML rollback — **most urgent**

v6 is `is_active=1` at 12.5% acc; v3 is the only good model. The gate prevents future damage but doesn't fix this. Two ways:

**Option A — one-off DB update (10 min, do this first):**
```sql
UPDATE ml_models SET is_active = 0 WHERE version IN (4, 5, 6);
UPDATE ml_models SET is_active = 1 WHERE version = 3;
```
Then restart the bot — [predictor.py](../src/ai_trade/ml/predictor.py) only reads the registry at init.

**Option B — startup auto-rollback (the right fix, 1–2 h):**
In `SignalQualityPredictor._load_active_model`, after loading the active row, run the same gate (`MIN_VAL_ACCURACY`, `MIN_TRAINING_TRADES`). If it fails, walk `ORDER BY version DESC` for the most recent passing row, mark the failing one `is_active=0` and the passing one `is_active=1`, emit a `notify_ml_rollback` email. This makes the gate symmetric: trainer blocks new, predictor heals existing.

Why both: A unblocks today's trading. B prevents the next time someone hand-promotes a bad version.

### 3.2 Other strategies still have no min_entry_price floor

The v2.4.1 floor is on `macd_divergence` + `ema_crossover` only. Price-bucket P&L breakdown across closed trades:

| Bucket | Trades | WR | Total P&L |
|---|---|---|---|
| <$2 | 10 | 20.0% | **+$168** |
| $2–5 | 13 | 61.5% | **−$801** |
| $5–10 | 7 | 28.6% | **−$298** |
| $10+ | 8 | 62.5% | **+$219** |

The <$2 bucket is actually profitable (`momentum` scalps win). The $2–10 bucket is where the damage concentrates — high WR but the losses gap-down on overnight holds (RGNT). The fix isn't a blanket floor across all strategies; it's **`hold_type=swing` strategies on sub-$5 = banned**. Concrete:

- Add `min_entry_price: 5.00` to `pullback`, `mean_reversion`. They're both swing.
- **Don't** add to `momentum`, `vwap`, `orb` — they're day/adaptive and the <$2 data says they work there.
- Consider a global gate in [signal.py](../src/ai_trade/strategy/signal.py): `if sig.hold_type == SWING and sig.entry_price < swing_min_entry_price` regardless of per-strategy floor. Less to forget when adding a new swing strategy.

### 3.3 Heat math is direction-blind (latent bug)

Sampled `trades` table:
```
JRSH  entry=3.86  stop=4.17  shares=204  risk=-62.73  (status=open)
```
Stop above entry on a long = data corruption OR a short being treated as long. The heat formula `(entry − stop) × shares` returns negative, which the heat-cap check then treats as "less risky than zero" and waves through. Two things:

1. **Investigate JRSH.** Look at its insertion path (`order_manager._adopt_untracked_position` or strategy-submitted bracket). It's likely an adopted position where the bracket-side detection got the wrong leg.
2. **Harden the math.** In [risk_manager.py](../src/ai_trade/risk/risk_manager.py) heat calc, use `abs(entry − stop) × shares` always, and assert sign matches `direction` field. A −$62 "risk" reading should `log.warning("trade_risk_sign_mismatch")` and rebroadcast as `+$62` of risk rather than silently subtracting from total heat.

### 3.4 The bot doesn't act on its own near-miss data

[strategy/signal.py:471](../src/ai_trade/strategy/signal.py#L471) `get_near_misses()` is plumbed and `analysis.filter_report_days: 7` logs the report nightly — but nothing closes the loop. The user is reading it manually. Two ideas worth scoping:

- **Auto-loosen the tightest chronic-near-miss filter** per strategy when its 14-day report shows >50% of rejections clustered on one threshold. Conservative: 5% knob nudge, capped at 20% of the original. Behind a feature flag.
- **Auto-disable a strategy** when its rolling 20-trade WR drops below 35% AND its `total_pnl` is negative. `bb_squeeze` was hand-disabled this way on 2026-05-05 — automate it.

## 4. Performance issues (literal — CPU/IO)

### 4.1 `main.py` is a 140 KB monolith

That's roughly 3000 lines. Every reader (including future-you) pays the navigation cost. Splitting it should reduce diff friction more than it improves runtime, but two refactors are worth doing:

- Move scheduled job bodies (`job_full_scan`, `job_evaluate`, `job_sync_positions`, `job_eod_*`, `job_ml_training`) to `scheduler/jobs.py`. That file already exists with thin stubs.
- Lift `_log_stock_trade_exit` and friends into a `monitoring/exit_hooks.py` — the logic is independent of `TradingBot` state and would be unit-testable in isolation.

### 4.2 `decisions` table is at 240,720 rows

The 14-day retention claim in [config/settings.yaml:289](../config/settings.yaml#L289) is set to `decision_retention_days: 14`, but the table is huge. Either the prune job isn't running, the date column it filters on isn't being indexed, or the prune is selecting too narrow a slice. Read the prune code (grep for `decision_retention_days`), then:

- Add an index on `decisions(timestamp)` if missing.
- Run `EXPLAIN QUERY PLAN` on the prune statement to confirm it's not a table scan.
- The decision_logger writes ~25k rows/day — that's a fair amount of I/O on SQLite. Batching the inserts (executemany) would help; even better, asyncify them so the trade loop doesn't block on DB writes.

### 4.3 Per-candidate strategy fan-out

[signal.py:135](../src/ai_trade/strategy/signal.py#L135) loops `for symbol in candidates: for strategy in self.strategies` — that's `n_candidates × n_strategies` `evaluate()` calls every 5 min. Each `evaluate()` does its own indicator math (`add_ema`, `add_rsi`, `add_atr`, ...) on the same `daily_bars` DataFrame. With 10 strategies × 25 candidates, the same EMA is computed 4–6 times per bar.

The fix is to compute indicators **once per symbol per cycle** in a `prepare_features(daily_bars)` step and pass that frame to every strategy. The indicator functions in [data/indicators.py](../src/ai_trade/data/indicators.py) are idempotent (`add_ema(df, [9,20,50])` is a no-op if columns exist), so the cleanup is: have the aggregator call all indicator functions up-front, then strategies just `getattr(self.config, ...)` and read columns.

Expected win: 30–40% reduction in per-cycle CPU under full load.

### 4.4 Database connection pattern is `with self._conn() as conn:` everywhere

Every read opens a new SQLite connection. For SQLite that's cheap (no network round trip) but it still serializes against writes. The connection-per-call pattern means the bot is opening **thousands** of connections per session. A single long-lived connection per thread (with `check_same_thread=False` and a `Lock`) would simplify and speed up the I/O path — but only worth doing if §4.2 hasn't already eliminated the row-count pressure.

### 4.5 `joblib.load` on every restart

[predictor.py:104](../src/ai_trade/ml/predictor.py#L104) loads the model file synchronously at init. v3's model is 124 KB; that's fast. But if you switch to a bigger model (LightGBM, ensemble) this becomes startup latency you'll feel. Pre-flight: keep the model size budget under 5 MB.

- Skip cooldown on a winning exit.
- Or, scale the cooldown by `pnl_pct`: 30 min for a >3% loss, 0 for a winner.

### 10.3 NEW bug found — console heat uses a non-existent key
[main.py:2270](../src/ai_trade/main.py#L2270) (the console/monitoring heat readout, separate from `risk_manager.check_portfolio_heat`) computes:
```python
total_risk = sum(abs(t.get("entry_price", 0) - t.get("stop_loss_price", 0)) * t.get("shares", 0) ...)
```
`get_open_trades()` rows have **`stop_loss`**, not `stop_loss_price`, so `.get("stop_loss_price", 0)` is always `0` → `total_risk = entry × shares` (full position value). Cosmetic — this feeds the console/email display, *not* the entry gate — but the displayed heat % is wildly wrong. **Fixed** in v2.4.2: on the current book this drops the displayed heat from 25.48% to 3.99%.

**Consolidated.** The two heat implementations are now one: the calc lives in `RiskManager.compute_portfolio_heat` (returns a fraction of equity, with the directional sign-mismatch logging inside it), and both `check_portfolio_heat` (the gate) and the `main.py` console display call it. The display was the buggy copy; removing the duplicate is what guarantees the two can't drift again. Verified both paths return identical heat (3.985%) on the live book and the gate still trips on a forced breach.
